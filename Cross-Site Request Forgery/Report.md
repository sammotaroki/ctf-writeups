# I Bought a $1,337 Jacket for One Cent

Nov 10, 2026 · @Sam

The online shop let our browser decide the price and the server took its word for it. This is the full run: the Burp and Firefox setup, the one parameter that gave us away, the exploit, and the fix that would have stopped it.

## The flaw&#32;

The shop let my browser decide the price, and the server just went along with it. No clever payload, nothing malformed. Just a normal request with one number quietly changed.

## The target

This one is from PortSwigger's Web Security Academy, in the Business Logic Vulnerabilities module. It's rated Apprentice.

The lab gives you a fake online shop. You log in with an account that already has $100 of store credit. That sounds fine until you see what you want to buy. There's a Lightweight "l33t" Leather Jacket sitting on the shelf for $1,337.00. If you missed the joke, 1337 reads as "leet", so someone on the PortSwigger team was having fun. I wanted that jacket. My $100 said no. So I went looking for a way around it.

## Setting up Burp and Firefox

I opened Burp Suite as a temporary project, since there was nothing here worth saving.

First the proxy. Under Proxy > Proxy settings I checked the listener was running on `127.0.0.1:8080` with Support HTTP/2 turned on. I set the request interception rules to fire only for traffic that's in scope, which keeps every other background request out of the way, and did the same for responses.

Next the scope. I copied the store's URL and added it under Target > Scope > Include in scope. Now Burp only pays attention to the shop.

The last piece is getting Firefox to actually talk to Burp, because out of the box it doesn't and nothing shows up. I went into Firefox's Network Settings, set Configure Proxy Access to the Internet to Manual proxy configuration, put `127.0.0.1` in the address with port `8080`, and ticked "Also use this proxy for HTTPS". If you'd rather not dig through settings every time, FoxyProxy and Burp's proxy do the same thing with one click. After that, everything was wired up.

## Recon: look before you touch

I left interception off for now. Before changing anything I wanted a picture of how the shop works. With Intercept off, I clicked around like a normal customer and added the jacket to the cart. Every request the browser made got logged under Proxy > HTTP history.

That history is the shop with its clothes off. It shows every endpoint the site hit while I was browsing. Logic bugs tend to hide in the gaps between steps, like the handoff from add to cart, to reviewing the cart, to checkout. That history is exactly where I wanted to look.

## The find

I scrolled back to the moment I added the jacket and found the request behind it. It's a `POST /cart`, and it carries the price right there in the body:

```
POST /cart HTTP/1.1
Host: <lab-id>.web-security-academy.net
Content-Type: application/x-www-form-urlencoded

productId=1&redir=PRODUCT&quantity=1&price=133700
```

Look at the end of that. `price=133700`, which is $1,337.00 in cents, and my browser is the thing sending it. The server is trusting the client to be honest about the price. That got a cynical little chuckle out of me, because that right there is the way in.

## Exploitation

If the server trusts whatever price my browser sends, then I just stop sending the honest one.

1. I turned Intercept on and added the jacket to the cart again to catch the `POST /cart` request.
2. In the body I found `price=133700` and changed it to `1`. That's one cent.
3. I forwarded the request.
4. I opened the cart and there was the jacket at $0.01. Since I was already in there, I grabbed a second jacket and threw in The Lazy Dog too, both at a cent each. Cart total came to three cents.
5. I turned interception off and placed the order.

That's it. The receipt is the fun part. It still lists the jacket at its catalog $1,337.00 and the Lazy Dog at $94.58, but the total charged was $0.03, and my store credit only dropped from $100.00 to $99.97. The shop showed one price and billed another, because the price it actually trusted was the one I sent.

Want the clean "for free" version for the headline instead? Send `price=0` rather than `1`, then grab the cart and solved screenshots again. The server doesn't check either way, so anything under your credit works.

## Root cause

This isn't a typo in the code. It's a trust problem.

The developers treated the browser as if it were part of their own system. It isn't. Everything that runs on the client side, whether that's a hidden form field, a JavaScript variable, or a request parameter, is fully in the user's hands. The price should only ever be looked up on the server, from the product catalog, using the product ID. The second a price gets sent from the client to the server as an input, it stops being a fact and turns into a suggestion.

## How you'd fix it

The fix is about as simple as the bug.

- Don't accept a price from the client at all. The browser should send the product ID and the quantity, nothing else. The server looks up the real price itself.
- Treat everything coming from the client as untrusted, hidden fields included. "The user can't see this field" is not a security control.
- Enforce it on the server every time. Client side checks are there to make the page feel quick, not to keep anyone honest.

## Takeaways

Logic bugs like this are my favorite kind, because nothing about the request looks wrong. It's completely valid. The flaw lives in an assumption the app made. That's also why scanners walk straight past these and people find them. You have to understand what the app is meant to do, then ask what happens if you don't cooperate.

If you take one thing from this, make it this. Stop staring at the web page and start watching the traffic. The page is the story the app wants to tell you. The HTTP history is what actually happened.
